طرح ساختِ پل رومیزیِ جدید برای ایجنت

بازطراحی از صفر: یک برنامهٔ واقعیِ ویندوزی که با یک دکمه به ایجنت وصل شود، ابزارها را مدیریت کند و برای کار روزانه نه به مرورگر نیاز داشته باشد و نه به سروری که مالک راه‌اندازی کند.

نسخهٔ پژوهشی، بازنگری اتصال Kling به CLI ـ ۲۷ سپتامبر ۲۰۲۶ · خروجی این سند «طرح ساخت» است، نه ادعای ساخته‌شدن یا آزموده‌شدن برنامهٔ تازه.

وضعیت کنونی: این سند طرح تاریخی است

از ۲ اکتبر ۲۰۲۶، ژینوس توصیف‌شده در این طرح پیاده‌سازی شده و نسخهٔ 0.8.1 روی رایانهٔ مالک نصب است. این فایل به‌عنوان سابقهٔ پژوهش اولیه نگهداری می‌شود؛ برای قابلیت‌های موجود و راهنمای استفاده به راهنمای کاربر انگلیسی، README فنی برنامه و HANDOFF جاری رجوع کنید. هیچ متن بعدی این طرح دربارهٔ «هنوز ساخته نشده» نمایانگر وضعیت امروز نیست. وجود این طرح مجوز انتشار، DM یا هزینه‌کرد نیست.

تصمیم اصلیسه صفحهمعماریGitHub و VPNاحراز هویت و ابزارهاامنیت فرمانعیب‌یابیمراحل و پذیرشمنابع

۱. تصمیم اصلی؛ قرار است چه چیزی ساخته شود؟

پیشنهاد من یک برنامهٔ بومی Windows با WPF و ‎.NET 10 است. برنامه با بستهٔ خودبسنده منتشر می‌شود؛ در استفادهٔ روزانه به اجرای دستی Node، npx، PowerShell، باز کردن وب‌سایت یا راه‌اندازی سرویس محلی نیاز ندارد. چون CLI رسمی Kling بر Node تکیه دارد، تهیهٔ یک‌بارهٔ پیش‌نیازِ سازگار باید در فرایند نصب برنامه مدیریت و روی Windows واقعی آزمایش شود؛ خودبسنده‌بودنِ رابط WPF به‌تنهایی CLI را بی‌نیاز از Node نمی‌کند. ‎.NET 10 نسخهٔ پشتیبانیِ بلندمدت است و مایکروسافت انتشارِ خودبسنده را برای برنامه‌های رومیزی مستند کرده است. راست‌به‌چپ واقعی در WPF از ابتدای طراحی، با FlowDirection=RightToLeft، پیاده می‌شود؛ کدها، نشانی‌های اینترنتی و نام متغیرها در بخش‌های جداگانه چپ‌به‌راست می‌مانند. [۵] [۱] [۱]

این برنامه پوستهٔ وب‌سایت، مرورگر جاسازی‌شده یا بازنویسی عجولانهٔ رلهٔ فعلی نیست. ساختار تازه از ابتدا جدا می‌شود؛ نسخهٔ قدیم تا زمان گذراندن آزمون‌های نسخهٔ جدید دست‌نخورده می‌ماند. فقط سه بخش اصلی در رابط کاربری وجود دارد: «اتصال»، «تنظیمات» و «لاگ».

تجربهٔ روزمره: مالک یک بار اطلاعات لازم را در «تنظیمات» وارد و ذخیره می‌کند؛ از آن پس برنامه را باز می‌کند، «اتصال» را می‌زند و تمام. بستن واقعی برنامه یا زدن «قطع ارتباط»، پذیرش فرمان‌های تازه را متوقف می‌کند. برنامه نباید پنهانی در سینی سیستم باز بماند؛ اگر قابلیت کمینه‌سازی به سینی بعداً اضافه شد، از «خروج» آشکارا متمایز است.

۲. سه بخشِ دقیقِ برنامه

الف) اتصال

دکمه‌های پررنگ و خوانای «اتصال» و «قطع ارتباط و بستن برنامه»، همراه با وضعیتِ خود برنامه، صندوق ارتباط GitHub، و هر ابزار به‌طور جداگانه نمایش داده می‌شوند. برای هر کدام «متصل»، «قطع»، «نیازمند ورود»، «اختلال شبکه» یا «در حال بررسی» و آخرین زمان بررسی دیده می‌شود؛ چراغ سبز یا قرمز بدون متنِ توضیحی کافی نیست. «اتصال» به معنای سالم‌بودن Kling یا Zernio نیست: سلامت مسیر فرمان و سلامت سرویس مقصد دو موضوع مستقل‌اند. ابزارهای عیب‌یابیِ خواندنی، از همین صفحه در دسترس‌اند، نه در صفحهٔ چهارم.

ب) تنظیمات

برای GitHub، Kling، Zernio و FLUX کارت پیش‌فرض می‌سازیم؛ در صورت نیاز کارتِ پورتال و دیگر سرویس‌ها نیز افزوده می‌شود. هر کارت تنها اطلاعات واقعاً لازم برای همان سرویس را می‌خواهد: کلید یا نشانی، وضعیت مجوز، تنظیم پراکسیِ همان ابزار، «ذخیره»، «تست اتصال» و نشانگر سبز/قرمز با علت خطا. کارت Kling استثناست: به‌جای گرفتن توکن، منطقهٔ حساب را با انتخاب مالک، نسخه/مسیر CLI، دکمهٔ «ورود» و وضعیت ورود نشان می‌دهد؛ هرگز محتوای فایل اعتبار CLI را نمی‌خواند یا نمایش نمی‌دهد. آزمونِ پیش‌فرض فقط خواندنی و بدون هزینه/انتشار است؛ مثلاً بررسی مخزن برای GitHub، kling who_am_i برای Kling و سلامت حساب برای Zernio. آزمونِ تولید تصویر یا ویدئو که احتمال هزینه دارد، جداگانه اجازه می‌خواهد. راهنمای Zernio بررسی سلامت حساب را از انتشار محتوا جدا می‌کند. [۱] [۲]

علاوه بر آن، کارت سفارشی استاندارد وجود دارد: «نام سرویس»، ردیف‌های «نام متغیر / مقدار» با افزودن و حذف ردیف، نوع مقدار (محرمانه/عادی)، آدرس API یا MCP، روش احراز هویت، و آزمونِ قابل‌تنظیمِ ایمن. مقدارِ محرمانه پنهان است، فقط با اقدام خود مالک آشکار می‌شود و در کپی/خروجی تنظیمات یا لاگ نمی‌آید. افزودن سرویس یا متغیر تازه نیازمند بازسازی EXE نیست. کارت‌ها برای پیکربندی و آزمون هستند؛ فهرست محدودی از دستورهای قابل اجرای ایجنت تعریف نمی‌کنند.

ج) لاگ

همهٔ رخدادهای عملیاتیِ قابل ثبت ــ اتصال/قطع، درخواست و پاسخ، ابزار، زمان، شناسهٔ درخواست، اجازهٔ مالک، نتیجه، مدت اجرا، کد خطا و تشخیص DNS/TLS/پراکسی ــ به شکل ساخت‌یافته در دستگاه ثبت می‌شود. فیلترِ «ابزار»، «زمان»، «موفق/ناموفق» و «سطح اهمیت» و دکمهٔ کپیِ ردیف یا لاگ فیلترشده وجود دارد. محتوای حساسی مانند رمز، توکن، کد OAuth و متنِ محرمانهٔ پاسخ‌ها پیش از نمایش، ذخیره و کپی پالایش می‌شود؛ پس «لاگ کامل» به معنی نشت اسرار نیست. لاگ‌های بزرگ سقف حجم، چرخش فایل و امکان خروجیِ پاک‌سازی‌شده دارند. [۱]

۳. ارتباط ایجنت با رایانه چگونه کار می‌کند؟

ایجنت ← پیامِ امضاشده/رمزگذاری‌شده در صندوق خصوصی GitHub ← برنامهٔ باز و متصل روی Windows ← API / Kling CLI / ابزارهای دیگر / فرمانِ مجاز ← نتیجهٔ پالایش‌شده از همان صندوق ← ایجنت

GitHub فقط صندوقِ انتقال درخواست و نتیجه است، نه سرورِ شخصیِ همیشه‌روشن و نه مرورگرِ واسط. برنامه روی رایانهٔ مالک با درخواست‌های خروجی به GitHub وصل می‌شود و ابزارها را مستقیماً از خود Windows فراخوانی می‌کند. سوی ایجنت یک کلاینتِ کوچکِ همین پروتکل لازم است؛ اما «Bridge مرورگر» و تب بازِ استودیو هیچ نقشی در اتصال عملیاتی ندارند. با بسته‌شدن برنامه، هیچ پردازشِ مخفی‌ای نباید فرمان بعدی را اجرا کند.

برای نمونهٔ اولیه، از یک مخزن خصوصیِ مجزا از مخزن کد و شاخه‌های کاری و API محتوای GitHub استفاده می‌کنیم. پیام‌ها شناسهٔ یکتا، مهلت انقضا، شناسهٔ نشست، وضعیت انجام و محدودیت اندازه دارند؛ نسخهٔ دومِ پیام تکراری دوباره اجرا نمی‌شود. در هر نشست، برنامه درخواست‌های نشست‌های قبلی را رد می‌کند. دسترسی GitHub به همان مخزن محدود است: در حالت ایده‌آل مجوز GitHub App محدود به آن مخزن، یا در نمونهٔ اولیه توکنِ ریزدانهٔ قابل لغو؛ هیچ توکنی داخل EXE یا سورس قرار نمی‌گیرد. سازوکار هویت فرستنده و تأیید محلیِ درخواست‌های خطرناک باید جدا از «خصوصی‌بودن مخزن» بررسی شود. [۱] [۱]

GitHub یک صفِ کم‌حجم با تأخیرِ چندثانیه‌ای است، نه کانالِ بلادرنگ یا محل ذخیرهٔ فایلِ رسانه‌ای/اسرار. نوشتن‌های هم‌زمان ممکن است تعارض بسازند؛ سهمیهٔ معمولِ API احراز‌هویت‌شده ۵۰۰۰ درخواست در ساعت است و محدودیت‌های ثانویه هم وجود دارند، پس پرس‌وجوی پی‌درپی ممنوع و فاصله‌گذاری/تلاشِ دوباره لازم است. محتوای commit حتی پس از حذف فایل می‌تواند در تاریخچه بماند. برای همین متن و خروجیِ محرمانه را خام در مخزن نمی‌گذاریم، ظرفیت/تأخیر را با آزمون واقعی می‌سنجیم و اگر کافی نبود، فقط با تصمیم جدید مالک راه انتقال دیگری طراحی می‌کنیم. [۱] [۱]

۴. آیا GitHub نیاز به VPN را برطرف می‌کند؟

پاسخ کوتاه: فقط در مسیر انتقال فرمان، شاید؛ برای اینترنتِ کل برنامه، خیر. اگر ایجنت و Windows هر دو به GitHub دسترسی داشته باشند، می‌توانند بدون داشتن IP عمومی، باز کردن پورت یا VPN مشترک فرمان/نتیجه را ردوبدل کنند. اما اگر خود رایانهٔ Windows نتواند به Kling، Zernio، FLUX یا نشانیِ مقصد برسد، دریافت فرمان از GitHub این مشکل را حل نمی‌کند. GitHub Contents API سرویسِ ذخیرهٔ فایل است، نه VPN یا پراکسی عمومیِ ترافیک. [۱]

پس برای هر ابزار آزمون جداگانهٔ DNS، TLS، زمان پاسخ، احراز هویت و پراکسی لازم است. برنامه ابتدا تنظیم پراکسی سیستم را آزمایش می‌کند و امکان پراکسی مجازِ اختصاصی برای هر ابزار را می‌دهد؛ موفقیت ورود در مرورگر نشانهٔ قطعیِ موفقیت درخواست‌های برنامه نیست. .NET پیکربندی پراکسی برای درخواست‌های HTTP را پشتیبانی می‌کند. راه‌حلِ دسترسی به سرویسِ مسدود یا مختل ــ مثلاً پراکسی یا مسیر شبکه‌ای مورد تأیید مالک ــ موضوعی مجزا از انتقال فرمان است؛ از این طرح نباید وعدهٔ «بدون VPN در همهٔ شرایط» برداشت شود. [۱]

۵. ورود موقت در مرورگر و اتصال ابزارها

Kling ـ تصمیم اصلاح‌شده: برنامه از CLI رسمی Kling استفاده می‌کند، نه کلاینت MCP در خود برنامه؛ برای همین ایجنت هم‌زمان نسخهٔ MCP مستقل نصب نمی‌کند. فرمانی که فرستادید، npx skills add klingai-tech/skills، «مهارتِ راهنمای ایجنت» را نصب می‌کند و به‌تنهایی نصبِ برنامهٔ اجرایی kling روی Windows نیست. برای اجرای CLI باید بستهٔ رسمی npm مناسب منطقهٔ حساب نصب شود: @klingai/cli-global یا @klingai/cli-cn؛ بستهٔ اشتباه انتخاب نمی‌کنیم و منطقه را از مالک می‌پرسیم. CLI به Node.js 18+ نیاز دارد. طراحی نصب باید کاری کند مالک برای استفادهٔ روزمره ترمینال یا npx را اجرا نکند؛ برنامه پس از تأیید مالک، نصب/نسخهٔ CLI را بررسی و راه‌اندازی یک‌باره را هدایت کند. این وابستگی و شیوهٔ توزیعش باید پیش از وعدهٔ «بدون پیش‌نیاز» روی Windows اثبات شود. [۱] [راهنمای مهارت رسمی]

ورود CLI برخلاف تصورِ بدون‌مرورگر نیست: دستور رسمی kling login مرورگر را برای OAuth باز می‌کند و به یک گیرندهٔ موقتی در 127.0.0.1 بازمی‌گردد؛ صاحب برنامه سروری را دستی راه نمی‌اندازد. پس از ورود، کارت Kling با kling who_am_i نتیجه را بررسی می‌کند؛ توکن در محل اعتبارنامهٔ خود CLI نزد کاربر Windows می‌ماند و برنامه آن را کپی نمی‌کند. برنامه فقط هنگام ورود یا تجدیدِ لازم، با اقدام مالک مرورگر را باز می‌کند و پس از موفقیت به پیش‌زمینه بازمی‌گردد. بستن خودکار تبِ مرورگر خارجی در همهٔ مرورگرها تضمین‌شدنی نیست؛ استفادهٔ روزمره بدون مرورگر ممکن است، اما ورود اولیهٔ رسمی بدون مرورگر نه. [۱] [راهنمای مهارت رسمی] [۱]

Zernio: تنها مسیر انتشار و اتصال شبکه‌های اجتماعیِ استودیو است؛ کارتِ مستقیم و مستقل برای YouTube، Instagram، Telegram یا Manus ساخته نمی‌شود. FLUX: اتصالِ قابل‌پیکربندی با کلید و نشانیِ ارائه‌دهندهٔ منتخب؛ هیچ ارائه‌دهنده یا هزینه‌ای از پیش فرض نمی‌شود. کارت‌های عمومی برای HTTP API و MCP امکان افزودن ابزارهای آینده را بدون بازطراحی برنامه می‌دهند. اسرار «Vault پورتال» فقط در سمت سرور پورتال مصرف می‌شوند؛ برنامهٔ رومیزی نباید بتواند آن‌ها را از پورتال استخراج کند. کلیدهایی که خود مالک به برنامه می‌دهد، مستقل و محلی نگهداری می‌شوند. [۲]

۶. فرمان‌های آزاد، ولی تحت اختیار مالک

موتور فرمان به چند دستور ازپیش‌تعریف‌شده محدود نیست: ایجنت می‌تواند درخواستِ HTTP با روش/نشانی/بدنهٔ دلخواه برای سرویسِ تأییدشده، فراخوانی ابزارهای کشف‌شدهٔ MCP، یا اجرای فرمان سیستم‌عامل را با پارامترهای ساخت‌یافته بفرستد. کارتِ پیش‌فرضِ ابزار به معنی محدودکردن قابلیت‌های آن نیست. با این حال «فرمان دلخواه از راه دور بدون کنترل» عملاً دسترسی کامل به رایانه و اسرار محلی می‌دهد؛ چنین کاری را نمی‌توان هم‌زمان نامحدود و ایمن نامید. OWASP نیز خطر اجرای فرمان سیستم‌عامل را روشن کرده است. [۱]

  • خواندن و آزمون بی‌هزینه: مطابق اجازهٔ نشستِ فعال؛ نشانی‌های مقصد، حجم پاسخ و زمان اجرا محدود و در لاگ ثبت می‌شود.
  • تغییر فایل، اجرای shell، نصب/به‌روزرسانی و درخواست به مقصد تازه: پیش‌نمایش دقیقِ فرمان و تأییدِ موردیِ مالک در خود برنامه؛ بازهٔ زمانی، پوشهٔ کار و دسترسی محدود؛ امکان لغو/قطع. فرمانِ ردشده هرگز اجرا نشود.
  • انتشار، ارسال پیام، خرید اعتبار یا هر هزینه‌کرد: اجازهٔ روشن، جداگانه و مربوط به همان اقدام؛ تأییدِ اتصال یا اجازهٔ فرمان عمومی جای آن را نمی‌گیرد.
  • اسرار: فقط نزد کارگزارِ ابزار استفاده شوند و خودِ مقدار برای ایجنت/لاگ ارسال نشود. ذخیره با DPAPI در محدودهٔ کاربر Windows و دسترسی فایل محدود؛ نه در چت، مخزن GitHub، EXE یا Vault سمت‌سرورِ قابل‌خواندن از کلاینت. DPAPI در برابر بدافزار یا فرمانِ آزادِ اجراشده با همان حساب Windows تضمین مطلق نمی‌دهد: اجرای OS باید در پردازش کم‌دسترسیِ جداگانه، دور از مخزن اسرار، و با تأیید مالک طراحی و روی Windows آزموده شود. [۱]

برای درخواست‌های راه‌دور، علاوه بر مجوز GitHub، امضا/چالشِ نشست، جلوگیری از تکرار، مهلت انقضا، قطع فوری و ثبتِ تصمیم مالک لازم است. اگر هویتِ پایدارِ ایجنت در محیط فعلی میسر نباشد، امنیت را با «اثر انگشت و جفت‌سازیِ تکراری» ظاهرسازی نمی‌کنیم؛ آن را به‌عنوان ریسک طراحی ثبت می‌کنیم و عملیات حساس را بدون تأیید محلی اجرا نمی‌کنیم.

۷. تشخیص و رفع اشکال، بدون ساخت دوباره برای هر خطا

در همان برنامه، ایجنت می‌تواند با اجازهٔ مالک «بستهٔ تشخیصیِ پاک‌سازی‌شده» درخواست کند: نسخهٔ برنامه، نسخه و در دسترس‌بودن Kling CLI، سلامت GitHub، DNS/TLS، پراکسی، وضعیت ورود از طریق آزمون who_am_i و زمان پاسخ هر ابزار، آخرین خطاها و هم‌بستگی درخواست‌ها؛ بدون خواندن فایل اعتبارنامهٔ CLI. صفحهٔ اتصال علت را به زبان ساده نشان می‌دهد: «GitHub در دسترس نیست»، «توکن منقضی شده» یا «Kling از این شبکه پاسخ نمی‌دهد»، نه فقط چراغ قرمز. آزمون‌ها مخرب و پرهزینه نیستند.

اصلاح نشانی سرویس، پراکسی، کلید، الگوی درخواست یا تنظیمِ کارتِ سفارشی درجا اعمال می‌شود؛ ایجنت می‌تواند تغییرِ پیشنهادی را بفرستد، اما ذخیرهٔ تغییر حساس پس از پیش‌نمایش و تأیید مالک انجام می‌شود. برای نقصِ خودِ کد، مسیرِ به‌روزرسانیِ امضاشده با حفظ تنظیمات و بازگشت به نسخهٔ قبلی لازم است؛ ClickOnce برای به‌روزرسانی و rollback برنامه‌های Windows مستند شده است، اما انتخاب نهاییِ بسته‌بندی پس از آزمونِ نصب و امضا تعیین می‌شود. خرابیِ خودِ فایل اجرایی، فایروال یا قطع اینترنت را همیشه نمی‌توان با یک فرمان داخل همان فایل اجرایی ترمیم کرد؛ گاهی به‌روزرسانی باینری یا اقدام دستیِ مالک لازم است. [۵]

۸. ترتیب ساخت و شرط تحویل

مرحلهخروجیِ قابل بررسیشرطِ گذر
صفر: اثبات امکانآزمون واقعی روی Windows مالک: دسترسی GitHub، هویت پایدار ایجنت بدون جفت‌سازیِ تکراری، انتخاب منطقهٔ حساب Kling توسط مالک، نصب CLI و Node سازگار، kling login با مرورگر موقت، kling who_am_i، مسیر شبکه و پراکسی هر ابزار.اگر CLI/ورود روی Windows یا GitHub در شبکهٔ مالک کار نکرد، پیش از توسعهٔ کامل طرح اصلاح شود؛ «ورود بدون مرورگر» وعده داده نشود.
یک: پوسته و تنظیماتبرنامهٔ بومی فارسی/راست‌چین، سه صفحه، Connect/Disconnect، کارت‌ها و نگهداری امن اسرار.استفادهٔ روزانه بدون مرورگر، سرور دائمی یا اجرای دستیِ Node/npm؛ پیش‌نیاز CLI در نصب یک‌باره مدیریت شود؛ دکمه‌ها در Windows واقعی خوانا باشند.
دو: مسیر فرمانصندوق خصوصی GitHub، کلاینتِ ایجنت، نشست/مهلت/تأیید/لغو، پاسخ و خطا.با Bridge مرورگر خاموش، فرمانِ خواندنی کار کند؛ پس از قطع یا بستن برنامه هیچ فرمان تازه‌ای اجرا نشود؛ پیام قدیمی تکرار نشود.
سه: ابزارهاCLI رسمی Kling به‌جای ادغام MCP مستقل، Zernio، FLUX و کارت/API/MCP سفارشی برای ابزارهای دیگر؛ آزمون سالم/ناسالم جداگانه.افزودن سرویس و متغیر جدید بدون rebuild؛ تست‌های Kling و دیگر ابزارها بی‌هزینه باشند؛ تولید/انتشار فقط با اجازهٔ جداگانه.
چهار: پایداری و ترمیملاگ کاملِ پالایش‌شده، فیلتر و کپی، عیب‌یابی، به‌روزرسانی امضاشده و بازگشت نسخه.خرابی پراکسی، OAuth، GitHub و مقصد از هم قابل تشخیص و با ثبت جزئیاتِ بدون اسرار باشند.
پنج: پذیرشنسخهٔ ساخته‌شده را روی Windows واقعی نصب و اجرا می‌کنیم، نه فقط آزمون واحد یا لاگِ ارسالی.مالک مسیر «باز کن ← اتصال ← کار ← قطع/خروج» را تأیید کند؛ آزمون خطرناک، انتشار و هزینه‌کرد بدون مجوز انجام نشود.

آزمون نهایی باید قطع وسطِ کار، درخواست هم‌زمان، پرشدن سهمیهٔ GitHub، خرابی پراکسی و OAuth، خروجیِ خیلی بزرگ، کپی لاگ بدون نشت کلید، قطع برنامه هنگام فرمان و نصب نسخهٔ جدید/بازگشت را هم پوشش دهد. فقط پس از آن دربارهٔ کنارگذاشتن نسخهٔ قدیم تصمیم می‌گیریم. اگر انتقال تنظیمات قدیمی لازم شد، با رضایت مالک و در همان حساب Windows، بدون استخراجِ اسرار به مخزن یا چت انجام می‌شود.

جمع‌بندی تصمیم: ساختِ بومی از صفر + GitHub به‌عنوان صندوق احتمالی فرمان + Kling از مسیر CLI رسمی روی Windows (نه MCP مستقل) + مرورگر فقط هنگام ورود رسمی + سه صفحهٔ مشخص + فرمان‌های باز با رضایت متناسب با خطر + تشخیص و به‌روزرسانی امن. انتخاب منطقهٔ حساب، نصب عملی Node/CLI و کیفیت مسیر GitHub روی Windows مالک باید قبل از پیاده‌سازی کامل راستی‌آزمایی شوند.

منابع اصلی پژوهش

  1. مستندات مایکروسافت دربارهٔ پشتیبانی ‎.NET، انتشار برنامهٔ رومیزی و راست‌به‌چپ در WPF.
  2. راهنمای رسمی Kling CLI، راهنمای مهارت رسمی CLI برای تفاوت نصب Skill/CLI، منطقهٔ حساب، Node و ورود مرورگری؛ RFC 8252 برای OAuth نرم‌افزار بومی.
  3. مستندات GitHub: Contents API، سهمیهٔ REST API و توکن‌های ریزدانه.
  4. مستندات اتصال و سلامت حساب‌های Zernio؛ DPAPI ویندوز و ClickOnce.
  5. راهنمای OWASP برای اجرای امن فرمان و لاگ‌گذاری؛ توضیح MDN دربارهٔ محدودیت بستن تب مرورگر.
طرح پژوهشیِ ساخت ـ بدون تغییر در برنامهٔ موجود، بدون اجرای فرمان روی Windows و بدون انتشار یا هزینه‌کرد.
