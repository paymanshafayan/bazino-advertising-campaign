## ۱. اهداف و غیر‌اهداف

**اهداف (از تصمیم‌های مالک):**
1. استفادهٔ روزانه: باز کردن برنامه ← «اتصال» ← کار ← «قطع ارتباط و بستن». هیچ اجرای دستی Node/npx/PowerShell، هیچ تب مرورگر و هیچ سرویس محلی.
2. سه صفحهٔ مشخص؛ کارت ابزار برای سرویس‌های اصلی + کارت سفارشی «متغیر/مقدار» بدون نیاز به rebuild.
3. موتور فرمان عمومی (HTTP، Kling CLI، Zernio، فرمان سیستم‌عامل، تشخیص، پیشنهاد تغییر تنظیمات) با **رضایت متناسب با خطر** در خود برنامه.
4. عیب‌یابی و اصلاح تنظیمات درجا (بدون نصب مجدد) + مسیر به‌روزرسانی امن با حفظ تنظیمات و امکان بازگشت.
5. لاگ کامل، ساخت‌یافته، فیلترشدنی، کپی‌شدنی و **پالایش‌شده از اسرار**.

**غیر‌اهداف (عمداً خارج از دامنه):**
- پوستهٔ وب، مرورگر جاسازی‌شده، Electron، بازنویسی برنامهٔ قدیمی `desktop-app/` یا وابستگی به Browser Bridge.
- اتصال مستقیم به YouTube/Instagram/Telegram/Manus (فقط از Zernio).
- ادغام مستقیم MCP برای Kling (فقط CLI). نصب هم‌زمان CLI و MCP ممنوع.
- هر انتشار، پیام، خرید اعتبار یا هزینه‌کرد خودکار.
- VPN/پراکسی عمومی؛ حل مسدودبودن سرویس‌ها از شبکهٔ مالک.

## ۲. معماری و ساختار پروژه

**فناوری:** C# 14 / .NET 10 (LTS) · WPF با `FlowDirection=RightToLeft` از ابتدا · الگوی MVVM (CommunityToolkit.Mvvm) · وابستگی‌های حداقلی و شناخته‌شده. سازگاری: Windows 10 و 11، x64.

**مسیر پیشنهادی:** `استودیوی تبلیغات و بازاریابی/marketing-app/` (نام زیرپوشه ASCII طبق قاعدهٔ نام‌گذاری؛ جدا از `desktop-app/` قدیمی). اگر مسیر غیر-ASCII روی runner برای MSBuild مشکل ساخت، جایگزین: `marketing-app/` در ریشهٔ ریپو (تصمیم #6).

```

├─ BazinoMarketing.sln
├─ Directory.Build.props              # net10.0، Nullable، نسخهٔ واحد برنامه
```

## ۳. مشخصات سه صفحه

### ۳.۱ اتصال
- دو دکمهٔ بزرگ و خوانا: **«اتصال»** و **«قطع ارتباط و بستن برنامه»**. «اتصال» یعنی شروع نظارت بر صندوق فرمان؛ قطع/بستن یعنی هیچ فرمان تازه‌ای پذیرفته نمی‌شود (بدون پردازش پنهان یا ماندن در سینی سیستم).
- کارت‌های وضعیت با **متن علت**، نه فقط چراغ: خود برنامه (نسخه، زمان اجرا)، صندوق GitHub (آخرین بررسی، سهمیهٔ باقی‌مانده)، و هر ابزار جداگانه: `متصل / قطع / نیازمند ورود / اختلال شبکه / در حال بررسی` + آخرین زمان بررسی. سلامت مسیر فرمان و سلامت هر سرویس دو چیز مستقل‌اند.
- بخش «نشست ایجنت»: نشست فعال (شناسه، اثر انگشت، زمان شروع/انقضا)، دکمهٔ «پایان نشست». درخواست نشست جدید همین‌جا با «تأیید/رد» ظاهر می‌شود.
- بخش «درخواست‌های در انتظار تأیید»: پیش‌نمایش دقیق فرمان (ابزار، روش، نشانی، پارامترها، کلاس خطر) و دکمه‌های «اجازه بده / رد کن»؛ فرمان ردشده هرگز اجرا نمی‌شود.
- ابزارهای عیب‌یابی فقط‌خواندنی همین‌جا: «آزمون همهٔ اتصال‌ها»، «بستهٔ تشخیصی پاک‌سازی‌شده» (کپی)، «باز کردن پوشهٔ لاگ».

### ۳.۲ تنظیمات
- **کارت‌های پیش‌فرض:** GitHub (ریپو، شاخه، توکن ریزدانه، فاصلهٔ بررسی)، Kling (منطقهٔ حساب `global`/`cn`، وضعیت Node/CLI، دکمهٔ «ورود»، وضعیت ورود — بدون خواندن یا نمایش فایل اعتبار CLI)، Zernio (کلید API، پایهٔ نشانی)، FLUX (ارائه‌دهنده/نشانی/کلید به انتخاب مالک؛ پیش‌فرض خالی).
- هر کارت: فقط فیلدهای لازم همان سرویس، پراکسی اختصاصی (اختیاری)، «ذخیره»، **«تست اتصال» فقط‌خواندنی و بی‌هزینه** (GitHub: خواندن ریپو + سهمیه؛ Kling: `who_am_i`؛ Zernio: سلامت حساب‌ها؛ FLUX: درخواست وضعیت/مدل‌ها اگر ارائه‌دهنده داشته باشد)، نشانگر سبز/قرمز با علت خطا، و کلیدهای مجوز: «اجازهٔ عملیات نوشتنی»، «اجازهٔ انتشار»، «اجازهٔ هزینه‌کرد» (پیش‌فرض همه خاموش).
- **کارت سفارشی استاندارد:** نام سرویس، نوع (HTTP API / MCP)، نشانی پایه، روش احراز هویت (بدون/Bearer/Header/Basic)، ردیف‌های «نام متغیر / مقدار / محرمانه؟» با افزودن/حذف، آزمون امن قابل‌تنظیم (فقط GET/مسیر مشخص). مقدار محرمانه پنهان است، فقط با اقدام مالک آشکار می‌شود و در خروجی تنظیمات/لاگ/پاسخ به ایجنت نمی‌آید. افزودن سرویس/متغیر تازه نیازمند rebuild نیست.
- «خروجی گرفتن از تنظیمات (بدون اسرار)» و «وارد کردن»؛ ایجنت می‌تواند **پیشنهاد تغییر** بفرستد، ذخیرهٔ تغییر حساس فقط پس از پیش‌نمایش و تأیید مالک.

### ۳.۳ لاگ
- رخدادها به شکل ساخت‌یافته (JSONL) در دستگاه: زمان، سطح، ابزار، شناسهٔ درخواست/نشست، کلاس خطر، تصمیم مالک، نتیجه، مدت، کد خطا، تشخیص DNS/TLS/پراکسی.
- فیلتر: ابزار، سطح، موفق/ناموفق، بازهٔ زمانی، جست‌وجوی متن؛ نمایش مجازی‌سازی‌شده برای حجم زیاد؛ «کپی ردیف»، «کپی لاگ فیلترشده»، «خروجی پاک‌سازی‌شده».
- **پالایش پیش از ذخیره/نمایش/کپی:** همهٔ مقادیر محرمانهٔ شناخته‌شده + الگوهای Bearer/توکن GitHub/کد OAuth/کوکی/URL حاوی credential با `***` جایگزین می‌شوند. سقف حجم فایل، چرخش روزانه، نگهداری محدود.

## ۴. صندوق فرمان GitHub و مدل امنیتی

**چرا همین ریپو/شاخه:** دسترسی GitHub این نشست (`arena-ai-coding-agent[bot]`) به همین ریپو و فقط همین شاخه محدود است؛ ریپو **خصوصی** است. ریپوی جداگانه بدون اعطای دسترسی به Arena قابل استفاده نیست (تصمیم #2).

**ساختار پوشه (روی همین شاخه):**
```
marketing-app-mailbox/
├─ README.md            # قواعد: هیچ راز/کوکی/کد OAuth/دادهٔ حساب؛ فقط پیام‌های رمزگذاری‌شده
├─ status.json          # ضربان برنامه: نسخه، متصل/قطع، آخرین بررسی، کلید عمومی برنامه، خلاصهٔ سلامت (بدون راز)
├─ sessions/<id>.json   # درخواست نشست ایجنت: کلید عمومی نشست، زمان، انقضا، دامنهٔ درخواستی
├─ cmd/<seq>-<id>.json  # فرمان امضاشده و رمزگذاری‌شده به کلید برنامه
└─ res/<id>.json        # پاسخ رمزگذاری‌شده به کلید نشست ایجنت + امضای برنامه
```

**پروتکل:**
- پاکت: `{v, id, session, seq, kind, risk, issued_at, expires_at, payload_enc, sig}`. رمزنگاری: ECDH P-256 + HKDF + AES-256-GCM؛ امضا: ECDSA P-256 (همه در .NET و WebCrypto نود موجودند؛ بدون وابستگی خارجی).
- `kind`: `diag` · `http` · `kling` · `zernio` · `os` · `settings-proposal` · `session-close`. `risk`: `read` · `write` · `publish` · `spend`.
- **نشست:** ایجنت در آغاز هر نشست کاری یک جفت‌کلید موقت می‌سازد و درخواست نشست می‌فرستد؛ برنامه آن را با شناسه و اثر انگشت به مالک نشان می‌دهد؛ **یک کلیک «تأیید»** برای همان نشست (با انقضا، مثلاً ۱۲ ساعت). فرمان از نشست تأییدنشده/منقضی نادیده گرفته و لاگ می‌شود. دلیل: کلید خصوصی ایجنت بین نشست‌های Arena پایدار نمی‌ماند و «هویت پایدارِ ساختگی» یا نگهداری کلید در ریپو ناامن است؛ این مدل صادقانه و کم‌زحمت‌ترین گزینه است (تصمیم #3).
- **سیاست اجرا:** `read` در دامنهٔ نشست تأییدشده خودکار (نشانی‌ها فقط از میزبان‌های کارت‌های تأییدشده، سقف اندازه/زمان)؛ `write`/`os`/مقصد تازه با تأیید موردی در برنامه؛ `publish`/`spend` فقط با کلید مجوز روشن در کارت **و** تأیید جداگانهٔ همان اقدام. تأیید اتصال یا نشست، جای این تأییدها را نمی‌گیرد.
- ضدتکرار: `seq` صعودی و فهرست `id`های دیده‌شده در هر نشست؛ انقضای پیش‌فرض ۱۰ دقیقه؛ سقف ۶۴KB برای هر پیام؛ خروجی بزرگ خلاصه/بریده می‌شود؛ رسانه هرگز از صندوق عبور نمی‌کند.
- بررسی صندوق فقط در حالت «متصل»، هر ۵ تا ۱۰ ثانیه با درخواست شرطی (ETag → پاسخ 304 به سهمیه نمی‌خورد)؛ نوشتن با Contents API و SHA فایل (بدون git محلی روی ویندوز). سهمیهٔ ۵۰۰۰ درخواست در ساعت با این فاصله امن است.
- پاک‌سازی: برنامه پس از پردازش، فرمان را حذف و پاسخ را می‌نویسد؛ ایجنت پس از خواندن، پاسخ را حذف می‌کند. **محدودیت پذیرفته‌شده:** هر پیام یک commit روی شاخه می‌سازد و تاریخچه، پیام‌های رمزگذاری‌شده را نگه می‌دارد؛ پیش از PR به `main` این پوشه کنار گذاشته می‌شود.
- سمت ایجنت: `tools/agent-client/` با Node 22 (`session open`، `send`، `wait`, `status`) از طریق `gh api`؛ ایجنت پیش از push کد باید `git pull --rebase` کند چون برنامه هم روی همین شاخه commit می‌کند.

|---|---|---|---|
| GitHub | توکن ریزدانه محدود به همین ریپو (Contents: خواندن/نوشتن)، در DPAPI | `GET /repos/{owner}/{repo}` + `rate_limit` | نوشتن پاسخ/وضعیت در صندوق (write، خودکار فقط برای صندوق) |
| Kling (CLI) | منطقهٔ حساب → بستهٔ `@klingai/cli-global` یا `@klingai/cli-cn`؛ Node ≥ 18 | `kling who_am_i` | تولید تصویر/ویدئو = `spend`؛ ورود با `kling login` فقط با اقدام مالک (مرورگر یک‌باره) |
| Zernio | کلید API | سلامت حساب‌ها و فهرست حساب‌های متصل | `POST /v1/posts` و اتوماسیون‌ها = `publish` |
| FLUX | ارائه‌دهنده/نشانی/کلید به انتخاب مالک (بدون پیش‌فرض) | درخواست وضعیت/فهرست مدل‌ها | هر تولید = `spend` |
| کارت سفارشی HTTP/MCP | نشانی، احراز هویت، متغیرها | GET امن قابل‌تنظیم / فهرست ابزارهای MCP | هر فراخوانی نوشتنی = `write` |
| فرمان سیستم‌عامل | — | فقط تشخیصی (نسخه‌ها، مسیرها) | هر اجرای shell = تأیید موردی، پوشهٔ کار محدود، مهلت، سقف خروجی، پردازش جدا |

**تهیهٔ پیش‌نیاز Kling بدون ترمینال برای مالک:** برنامه با تأیید مالک یک بار Node LTS قابل‌حمل (zip رسمی) را در `%LOCALAPPDATA%\BazinoMarketing\runtime\node\` می‌گذارد و بستهٔ CLI منطقهٔ انتخاب‌شده را با `npm install --prefix` در `runtime\kling\` نصب می‌کند (بدون دسترسی ادمین و بدون تغییر PATH سیستم). اجرا: `node <cli>\dist\cli.js …` با محیط کنترل‌شده. جزئیات نشانی/نسخه‌ها هنگام پیاده‌سازی از منابع رسمی تطبیق داده می‌شود (تصمیم #7). نشانی‌های Zernio طبق دانش قبلی استودیو هستند و هنگام پیاده‌سازی با مستندات رسمی روز بازبینی می‌شوند.

## ۶. اسرار، ذخیره‌سازی و پالایش

- مسیر داده: `%LOCALAPPDATA%\BazinoMarketing\` شامل `settings.json` (غیرمحرمانه)، `secrets.bin` (هر مقدار جداگانه با DPAPI در محدودهٔ کاربر ویندوز)، `keys\app-identity.bin` (کلید برنامه، DPAPI)، `logs\app-YYYYMMDD.jsonl`، `runtime\` (Node/CLI)، `sessions\approved.json`.
- اسرار فقط داخل Handler همان ابزار مصرف می‌شوند؛ ایجنت هرگز مقدار خام را نمی‌بیند. Redactor مقادیر محرمانهٔ ثبت‌شده و الگوهای شناخته‌شده را پیش از هر ذخیره/نمایش/کپی/پاسخ پالایش می‌کند؛ آزمون واحد «هیچ راز در لاگ/پاسخ» اجباری است.
- برنامه فایل اعتبار Kling CLI را نمی‌خواند و کپی نمی‌کند؛ Vault پورتال از این برنامه دست‌نیافتنی است.
- DPAPI در برابر بدافزار/فرمانی که با همان حساب ویندوز اجرا شود مصونیت مطلق نمی‌دهد → اجرای `os` در پردازش جداگانه و فقط با تأیید موردی؛ این ریسک در README ثبت می‌شود.

## ۷. ساخت، توزیع و به‌روزرسانی

**Workflow `marketing-app-ci.yml` (ریشهٔ ریپو):**
- `on: push` فقط شاخهٔ `arena/01a0e1c3-bazino-gamenet-portal` با فیلتر مسیر `marketing-app/**` و خودِ workflow؛ به‌علاوه `workflow_dispatch`.
- Job ۱ `core-tests` روی `ubuntu-latest` (ارزان، ~۲–۳ دقیقه): `dotnet test` هستهٔ غیر-UI.
- Job ۲ `windows-build` روی `windows-latest`، **فقط وقتی پیام commit شامل `[build]` باشد یا dispatch شود** (تصمیم #8): `dotnet test` (شامل تست‌های DPAPI) → `dotnet publish -c Release -r win-x64 --self-contained -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true` → اجرای `BazinoMarketing.exe --render-screenshots` → `SHA256SUMS` → انتشار با `softprops/action-gh-release@v2` روی تگ `marketing-app-dev-<run>` به‌صورت پیش‌انتشار (EXE + SHA256SUMS + zip اسکرین‌شات‌ها) → commit اسکرین‌شات‌های کوچک به `visual-testing/marketing-app/<run>/`.
- `permissions: contents: write`، `concurrency` با لغو اجرای قبلی، `timeout-minutes: 25`. **هیچ `upload-artifact`** استفاده نمی‌شود.
- بودجهٔ دقیقه: runner ویندوز با ضریب ۲ حساب می‌شود؛ یک build کامل حدود ۸–۱۲ دقیقهٔ واقعی ≈ ۱۶–۲۴ دقیقهٔ محاسباتی. اگر حساب روی طرح رایگان باشد (۲۰۰۰ دقیقه/ماه)، هدف: حداکثر ۱–۳ build در هر نشست کاری. Job لینوکس در هر push اجرا می‌شود.

**نصب برای مالک:** دانلود EXE از Release → اجرا (بدون نصب‌کننده؛ نسخهٔ اول). چون گواهی امضای کد نداریم، SmartScreen هشدار «ناشر ناشناس» می‌دهد؛ SHA256 در Release برای راستی‌آزمایی است. `build/publish.ps1` همان مراحل را برای ساخت محلی روی Windows مالک اجرا می‌کند (اگر Actions در دسترس نبود).

**به‌روزرسانی (فاز ۴):** «بررسی نسخهٔ جدید» در برنامه آخرین Release را می‌خواند، EXE را دانلود و SHA256 را تأیید می‌کند، نسخهٔ فعلی را به‌عنوان `previous.exe` نگه می‌دارد و با تأیید مالک جایگزین می‌کند؛ تنظیمات در `%LOCALAPPDATA%` دست‌نخورده می‌مانند؛ «بازگشت به نسخهٔ قبلی» یک کلیک است. ClickOnce/MSIX فقط اگر بعداً امضا و نیاز واقعی داشتیم.

## ۸. راهبرد آزمون و بازبینی بصری

1. **تست واحد Core (هر push):** رفت‌وبرگشت رمزنگاری، رد پاکت منقضی/تکراری/بدامضا/نشست غلط، طبقه‌بندی خطر و سیاست تأیید، Redactor (هیچ نشت راز)، مهاجرت تنظیمات، Handlerها با HTTP ساختگی و پردازش ساختگی برای CLI، فیلتر لاگ. روی ویندوز: DPAPI.
2. **اسکرین‌شات خودکار UI (هر build ویندوز):** حالت `--render-screenshots` هر سه صفحه و دیالوگ‌های تأیید را با دادهٔ نمونه در ۱۲۸۰×۸۰۰ و ۱۰۲۴×۷۶۸ به PNG رندر می‌کند (بدون نیاز به کلیک). ایجنت PNGها را از ریپو می‌کشد و **واقعاً می‌بیند** (قاعدهٔ بازبینی بصری سخت‌گیرانه): راست‌چینی، خوانایی دکمه‌ها، بریدگی متن، تضاد رنگ.
3. **Smoke اختیاری (فاز ۴):** FlaUI روی runner ویندوز: اجرا، کلیک «اتصال» با صندوق خاموش، تغییر وضعیت، «قطع و بستن».
4. **پذیرش روی Windows واقعی مالک (هر فاز):** فهرست کوتاه آزمون در README؛ مالک نتیجه/اسکرین‌شات را گزارش می‌کند؛ ایجنت فقط با اجازه، فرمان‌های آزمایشی می‌فرستد.
5. **سناریوهای شکست (پیش از پذیرش نهایی):** قطع وسط فرمان، فرمان هم‌زمان، پرشدن سهمیهٔ GitHub، خرابی پراکسی/OAuth، خروجی خیلی بزرگ، کپی لاگ بدون نشت کلید، بستن برنامه هنگام فرمان، به‌روزرسانی و بازگشت.

## ۱۲. آنچه بدون مجوز جداگانه انجام نمی‌شود

ورود به هیچ حسابی از طرف مالک؛ هر تولید هزینه‌دار (Kling/FLUX)؛ هر انتشار/پیام (Zernio)؛ اجرای فرمان OS روی دستگاه مالک؛ تغییر کد/تنظیمات پورتال یا `main`؛ آوردن workflowهای قدیمی؛ استفاده از Browser Bridge؛ قرار دادن هر راز در ریپو/چت/لاگ. طبق قانون ۳، پس از هر فاز مستندات و HANDOFF با نتیجهٔ واقعی (تست‌شده/تست‌نشده/مانع) به‌روز و به همین شاخه push می‌شود.
