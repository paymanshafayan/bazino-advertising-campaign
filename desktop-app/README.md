# Bazino Marketing Studio — نسخهٔ بدون Electron

برنامهٔ مستقل Windows: یک **launcher بومی PowerShell/ps2exe**، Node.js همراهِ بسته، و رابط کاربری در مرورگر **محلی** (`127.0.0.1:59670`). بستهٔ Windows هم با workflowهای GitHub Actions و هم **به‌صورت محلی با PowerShell** ساخته می‌شود؛ Actions محل اجرای شبانهٔ APIها یا ذخیرهٔ رمزها نیست. این معماری از شیوهٔ آزمودهٔ [`browser-bridge-build-manual-fa.md`](https://github.com/paymanshafayan/bazino-gamenet-portal/blob/arena/01a089a9-bazino-gamenet-portal/browser-bridge-build-manual-fa.md) الهام گرفته، اما runtime این استودیو از پل قدیمی `cdp-bus` استفاده نمی‌کند. برنامهٔ Electron قبلی جایگزین شده است.

> **وضعیت تأیید (۲۰۲۶-۰۹-۲۶):** آزمون‌های Node و syntax check محلی موفق شده‌اند؛ آزمون اجرای اسکریپت ساخت تازه روی Windows و بررسی GUI/DPAPI هنوز انجام نشده‌اند. در آخرین تلاش ثبت‌شدهٔ GitHub برای Studio Bridge (۰۵:۱۷ UTC)، آپلود باز هم با `Artifact storage quota has been hit` شکست خورد؛ بررسی ۰۵:۲۸ UTC شمار artifact و cache این ریپو را صفر نشان داد. رفع سهمیه یا وجود EXE قابل دانلود از Actions تأیید نشده است. اجرای واقعی Windows/DPAPI، feedها در شبکهٔ مالک، گیت روی اینترنت و اتصال حساب‌های Zernio/Kling/MCP تازه هنوز تأیید نشده‌اند. مستندِ دامنهٔ تغییر پژوهش/نشر پیشین: [ماتریس دسترسی و اجرای دو سند](../Doc/access-and-execution-matrix-fa.md).

## ساخت محلی روی Windows با PowerShell (بدون آپلود GitHub)

فایل [`build-local.ps1`](build-local.ps1) بستهٔ **استودیو** و در صورت انتخاب، فایل اجرایی **پل Bazino Studio Bridge** را روی رایانهٔ خودتان می‌سازد؛ به سهمیهٔ artifact گیت‌هاب نیاز ندارد. سورس کامل این پوشه باید روی Windows موجود باشد (از همان شاخهٔ کاری دریافت و استخراج کنید). از داخل همین پوشه در **Windows PowerShell 5.1 نسخهٔ ۶۴بیتی** اجرا کنید:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\build-local.ps1 -Target Studio -InstallPs2Exe
# اگر هر دو برنامه را می‌خواهید:
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\build-local.ps1 -Target All -InstallPs2Exe
```

برای استودیو **Node.js x64 نسخهٔ 22.12 یا جدیدتر همراه npm** لازم است؛ برای ساخت فقط پل، `-Target Bridge` نیاز به Node ندارد. اسکریپت وجود ماژول `ps2exe` را بررسی می‌کند؛ `-InstallPs2Exe` فقط در صورت نیاز نصب آن از PowerShell Gallery را برای کاربر جاری مجاز می‌کند. برای نصب وابستگی‌های npm/ماژول ساخت، اینترنت لازم است؛ **توکن GitHub، رمز حساب و کلید سرویس‌ها لازم نیست** و هیچ فایل ساختی به گیت‌هاب آپلود نمی‌شود. نصب `ps2exe` و `npm ci` روی همان سیستم انجام می‌شود؛ پیش از اجرا سورس و وابستگی‌ها را بررسی کنید.

اسکریپت آزمون‌ها و بررسی نحوی سورس را اجرا می‌کند، فقط فایل‌های لازم را بسته‌بندی می‌کند، هدر EXE و self-test بدون GUI/شبکه را می‌سنجد و SHA256 خروجی را چاپ می‌کند. خروجی‌ها در `dist\local\BazinoMarketing-Windows-x64.zip` و، با `-Target All` یا `Bridge`، در `dist\local\BazinoStudioBridge.exe` قرار می‌گیرند. **فایل ZIP استودیو باید کامل استخراج شود** تا `BazinoMarketing.exe`، `node.exe` و پوشهٔ `app` کنار هم بمانند؛ EXE تنها کافی نیست. خروجی‌ها امضای دیجیتال ندارند. اگر فایلی از قبل وجود داشته باشد، اسکریپت به‌جای جایگزینی متوقف می‌شود؛ برای ساخت مجدد و بازنویسی آگاهانه `-Force` بدهید. ساخت محلی این اسکریپت هنوز روی دستگاه Windows مالک اجرا/تأیید نشده است.

## ساخت دو برنامهٔ متمایز با GitHub Actions

مالک هر دو workflow را **دستی در GitHub** روی شاخهٔ `arena/01a0d4ee-bazino-gamenet-portal` ساخته است؛ الگوهای متناظر در سورس نگه داشته شده‌اند:

| فایلِ workflow در ریشهٔ ریپو | سورس الگو | خروجی |
|---|---|---|
| `.github/workflows/build-marketing.yml` | [`workflow-build-marketing.yml`](workflow-build-marketing.yml) | artifact `BazinoMarketing-Windows-x64` با ZIP شامل `BazinoMarketing.exe`، `node.exe` و `app/` |
| `.github/workflows/build-studio-bridge.yml` | [`browser-link/workflow-build-studio-bridge.yml`](browser-link/workflow-build-studio-bridge.yml) | artifact `BazinoStudioBridge-Windows` با **`BazinoStudioBridge.exe`**؛ عنوان پنجره **Bazino Studio Bridge** |

ساخت دستی فایل‌ها اجرای اولیه را آغاز کرد، اما آپلود هر دو artifact با خطای **`Artifact storage quota has been hit`** متوقف شد. مالک artifactها را با CLI پاک کرده و `total_count: 0` دیده شد؛ این **اثبات بازیابی سهمیهٔ آپلود نیست**. بدون درخواست تازهٔ مالک، برای آزمون دوباره workflow را اجرا نکنید. پس از مجوز و اجرای تازه، در Actions نام‌های **Build Bazino Marketing Studio** و **Build Bazino Studio Bridge** و تست‌ها/هش SHA256 را بررسی کنید. فایل اجرایی امضا نشده است؛ ZIP بازاریابی باید *کامل* استخراج شود و launcher، Node و `app/` کنار هم بمانند. به‌روزرسانی کد برنامه روی این شاخه ممکن است دوباره اجرای خودکار build را فعال کند؛ وجود خروجی تا موفقیت upload تأیید نمی‌شود.

## پل مرورگر استودیو و استفاده پس از ساخت

پل قدیمیِ وصل‌شده فقط شاخهٔ `cdp-bus` را می‌بیند و این نشست مجاز به نوشتن روی آن نیست. نسخهٔ متمایز [Bazino Studio Bridge](browser-link/README.md) پس از build روی شاخهٔ مجاز کار می‌کند. برای جلوگیری از تداخل، در پل قبلی **Disconnect** بزنید، Chrome اختصاصی (پورت ۹۳۳۴) را باز نگه دارید و `BazinoStudioBridge.exe` را روی Windows باز کرده **Connect** بزنید. از توکن DPAPI ذخیره‌شدهٔ همان کاربر استفاده می‌کند؛ توکن را در چت/ریپو نگذارید. تا heartbeat نسخهٔ جدید دیده نشود، ادعای کنترل مرورگر یا تکمیل OAuth نداریم. این کانال CDP خام فقط برای کار کوتاه و بدون انتقال رمز/کوکی/کد OAuth است.

برای توسعهٔ سورس: `npm ci && npm test && npm run check`. دستور `npm start` برای **Windows مالک** است؛ در لینوکسِ ایجنت عمداً بدون ذخیرهٔ اعتبارنامه اجرا نمی‌شود. دکمهٔ «بستن برنامه» سرور محلی و اتصال GitHub را قطع می‌کند؛ در نسخهٔ جدید، **بستن آخرین تبِ رابط نیز پس از مهلت کوتاهِ بارگذاری مجدد، سرور را خاموش و پورت 59670 را آزاد می‌کند**. بستن launcher هم از سمت Node پایش می‌شود. برای login در Kling تب اصلی استودیو را باز نگه دارید: callback فقط روی **همان ویندوز** در `http://127.0.0.1:59677/kling-callback` شنیده می‌شود و از باز شدن مرورگر تا ۱۰ دقیقه فرصت دارد؛ بستن استودیو تلاش ناتمام را لغو می‌کند. اگر callback هنوز خطا دارد، فقط متن خطای مرورگر و قسمت **host/port/path** را گزارش کنید؛ `?code=...`، `state` یا URL کامل را هرگز ارسال نکنید. Node/PowerShell جداگانه برای **اجرای ZIP آماده** لازم نیست چون ZIP همراه Node.exe و launcher است؛ برای **ساخت محلی** پیش‌نیازهای بخش بالا لازم‌اند.

**اجرای دوبارهٔ `BazinoMarketing.exe`:** launcher قبل از ساخت سرور جدید، فقط `127.0.0.1:59670` را بررسی می‌کند. اگر سرور **قابل‌شناسایی استودیو** (حتی نسخهٔ قبلی بدون نشانگر جدید) اجرا باشد، با توکن جلسهٔ همان سرور فرمان `app:stop` را می‌فرستد، حداکثر ۱۲ ثانیه برای آزاد شدن پورت منتظر می‌ماند و سپس نسخهٔ تازه را اجرا می‌کند؛ دو launcher هم‌زمان در مرحلهٔ شروع نوبت‌بندی می‌شوند. فرایند مالک پورت به زور kill نمی‌شود. هنگام راه‌اندازی مجدد، login ناتمام یا کار در حال انجام ممکن است قطع شود؛ قبل از آن وضعیت انتشار/هزینه را بررسی کنید. اگر پورت را برنامه‌ای ناشناس یا سروری بی‌پاسخ گرفته باشد، **بدون دست‌زدن به آن** پیام خطا می‌بینید.

فقط برای عیب‌یابیِ این حالتِ استثنایی، در PowerShell با `Get-NetTCPConnection -LocalPort 59670 -State Listen | Select-Object OwningProcess` شناسهٔ فرایند را ببینید. پیش از بستن دستی، با `Get-CimInstance Win32_Process -Filter "ProcessId = <PID>" | Select-Object CommandLine` مطمئن شوید واقعاً `node.exe` همین استودیو و `app\\src\\server.cjs` است؛ **فرایند ناشناخته را متوقف نکنید**. سپس، در صورت نیاز، فقط همان فرایند را با `Stop-Process -Id <PID>` ببندید. این کار توکن‌ها را منتقل نمی‌کند و رفع سهمیهٔ artifact گیت‌هاب هم نیست.

## گیت قابل‌پیکربندی برای API، متن وب و MCP (افزودهٔ این نسخه)

**یک‌بار نصب/به‌روزرسانی این نسخه لازم است**؛ بعد از آن برای اضافه‌کردن اتصال جدیدِ سازگار نیازی به طراحی/نصب مجدد نیست. در نمای **«گیت دسترسی آنلاین»** برنامهٔ محلی Windows:

1. **برای استخراج مطلب:** نشانی عمومی `https://...` را در بخش «خواندن متن» وارد کنید. یا ایجنتِ جفت‌شده با `node agent-client.cjs web 'https://news.example.com/article'` همان نشانی را از طریق relay امضاشده/رمزگذاری‌شده می‌فرستد و متن/عنوان/URL/زمان مشاهدهٔ پاسخ واقعی را دریافت می‌کند. این متن **منبع را تأیید نمی‌کند**؛ برای گزارش/نشر، مقالهٔ اصلی و شاهد مستقل را جدا بررسی کنید.
2. **برای API جدید:** شناسهٔ ثابت، نام و **HTTPS base URL** (مثلاً `https://api.example.com/v1`)، نوع `api` و احراز هویت `none`، `Bearer` یا نام header کلید (مثلاً `X-API-Key`) را وارد کنید. کلید/توکن فقط در *فیلد رمز* همین دستگاه درخواست می‌شود؛ نه در چت، CLI، GitHub، کد یا مرورگر دیگری. با پنجرهٔ تأیید بومی Windows مقصد و دسترسی ایجنت را تأیید کنید. مسیر درخواست مثل `/games?limit=10` به نشانی پایه افزوده می‌شود. بدون کلید هم API عمومی ممکن است کار کند. درخواست‌های `GET/HEAD` خواندنی فرض می‌شوند؛ `POST/PUT/PATCH/DELETE` همیشه تأیید موردی مالک می‌خواهند. بعضی سرویس‌ها حتی GET را هزینه‌دار/اثرگذار می‌کنند؛ به سرویس فقط پس از خواندن قرارداد/مستنداتش دسترسی ایجنت بدهید.
3. **برای MCP راه‌دور:** نوع `mcp`، نشانی **مستقیم endpoint Streamable HTTP** و در صورت پشتیبانی سرویس، `none`، `Bearer` یا OAuth/PKCE را برگزینید. OAuth تنها با دکمهٔ ورود **روی مرورگر مالک** و callback محلی `127.0.0.1:59678/gateway-callback` شروع می‌شود؛ رمز و توکن در vault محلی محافظت‌شده می‌ماند. ابزارها/منابع/پرامپت‌ها از **سرور زنده** فهرست می‌شوند. نام ابزار «خواندنی» ممکن است فریبنده باشد: **هر `tools/call` مستقل از گزینهٔ autoApproveWrites تأیید موردی Windows** دارد. درخواست relay هرگز به‌جای مالک صفحهٔ OAuth باز نمی‌کند. برای MCP رسمی Kling همچنان از پنل اختصاصی Kling با `who_am_i` استفاده کنید؛ گیت جایگزین آن مسیر نیست.
4. **سطح دسترسی هر اتصال**: `none` (پیش‌فرض: فقط خود مالک)، `read` (فقط GET/HEAD و فهرست/خواندن منابع و پرامپت‌ها)، یا `approved-writes` (خواندن + نوشتن/API و فراخوانی ابزار MCP با تأیید مستقل مالک). ایجنت تنها فهرست اتصال‌های **اشتراک‌داده‌شده بدون مقدار کلید** را می‌بیند. تغییر مقصد، نوع یا احراز هویت کلید/OAuth قبلی را پاک می‌کند؛ حذف اتصال هم راز آن را از Vault محلی پاک می‌کند. بازپس‌گیری مجوز نزد خودِ سرویس را در تنظیمات حساب انجام دهید.

پس از جفت‌سازی مطابق بخش relay، **فقط با اجازهٔ مشخص مالک** از این فرمان‌ها روی شاخهٔ ثابت استفاده کنید:

```text
node agent-client.cjs connectors
node agent-client.cjs web 'https://news.example.com/article'
node agent-client.cjs service vendor-api GET '/games?limit=10'
node agent-client.cjs service vendor-api POST '/items' '{"topic":"example"}' --confirm-write
node agent-client.cjs mcp-server vendor-mcp tools
node agent-client.cjs mcp-server vendor-mcp resources
node agent-client.cjs mcp-server vendor-mcp read-resource 'guide://latest'
node agent-client.cjs mcp-server vendor-mcp prompts
node agent-client.cjs mcp-server vendor-mcp get-prompt brief '{"theme":"gaming"}'
node agent-client.cjs mcp-server vendor-mcp call lookup '{"q":"gaming"}' --confirm-write
```

`--confirm-write` **به‌تنهایی مجوز انتشار، ارسال پیام یا هزینه‌کرد نیست**: درخواست/محدودهٔ مصوب در گفتگو و تأیید مجدد پنجرهٔ محلی لازم‌اند. relay روی GitHub به شاخهٔ ثابت و محیط جفت‌شده و worktree تمیز نیاز دارد؛ این فرمان‌ها بدون اتصال مالک به‌صورت زنده کاری انجام نمی‌دهند. برای API جدید، idempotency و وضعیت نتیجهٔ نامطمئن را بر اساس مستندات همان سرویس بررسی کنید؛ نوشتن نامطمئن را تکرار کور نکنید. ثبت سرویس از agent-client قابل انجام **نیست**؛ کلیدها در تنظیماتِ Windows مالک هستند.

**مرز بازاریابی:** ارسال پست/پیام به شبکه‌های اجتماعی فقط از مسیر اختصاصی **Zernio**، با کشف حساب زنده و کنترل‌های موجود انجام شود؛ گیت عمومی جایگزین preflight حساب‌ها یا مجوز مستقل انتشار نیست.\n\n**حدود فنی/امنیتی:** فقط hostname عمومی HTTPS روی پورت ۴۴۳؛ آدرس IP، شبکهٔ داخلی/metadata، redirect، شناسه/کلید در URL و DNS rebinding رد می‌شوند. پاسخ عمومی تا ۲ MiB در transport، خواندن صفحه تا ۱ MiB (متن خروجی حداکثر ۳۲ هزار کاراکتر) و API تا ۵۱۲ KiB محدود است؛ حداکثر ۳۰ اتصال. فقط HTML/متن/JSON/XML بدون اجرای JS، کوکی، render، login، paywall، CAPTCHA، فرم، فایل دوتایی/PDF یا upload عمومی خوانده می‌شود. MCP فعلاً **remote Streamable HTTP** است، نه `stdio` محلی یا سرور فقط-SSE؛ OAuth برای API دلخواه، proxy خصوصی، header دلخواهِ غیرکلید و بارگذاری حجیم تعبیه نشده‌اند. قابلیت هر سرویس به API، منطقه، طرح/هزینه و مجوز واقعی حساب شما وابسته است؛ «تمام موارد آنلاین» دسترسی جادویی یا دورزدن حقوق سرویس نیست. مقصدهای اختصاصی Zernio/Cloudflare و Kling از گیت دوباره ثبت نمی‌شوند تا پیش‌بررسی انتشار، محدودهٔ FLUX و راستی‌آزمایی هویت Kling دور زده نشوند.

## امکانات و امنیت

| ابزار | مسیر فنی و شرط واقعی |
|---|---|
| **Zernio (اصلی)** | API یکپارچه برای انتشار/زمان‌بندی، حساب‌ها و گزارش‌ها؛ YouTube، Telegram و Instagram فقط با حساب‌های متصل به خود Zernio و `platform`/`accountId` هدف‌گیری می‌شوند. برای استفاده از API محلی، کلید Zernio روی Windows در DPAPI ثبت می‌شود؛ **از Vault پورتال استخراج نمی‌شود**. بارگذاری رسانه با presign Zernio، سپس تأیید جداگانه برای ایجاد پست؛ برای `POST /v1/posts`، استفاده از `Idempotency-Key` تصادفی مختص **همان پست منطقی** با امکان retry در بازهٔ ۲۴ ساعت؛ با بدنهٔ متفاوت همان کلید را به پست تازه ندهید. پس از نتیجهٔ نامطمئن، پیش از درخواست تازه وضعیت پست را بررسی کنید. |
| **FLUX پیش‌فرض** | باز کردن `https://bazino.pro/admin/content` در مرورگر مالک و استفاده از سرویس `MediaGenService` پورتال. توکن و Account ID موجود Cloudflare فقط در Vault سرور پورتال می‌مانند؛ ورود به حساب پورتال و تأیید هزینه آنجا لازم است. تصویر تولیدشده در کتابخانهٔ پورتال ذخیره می‌شود، نه خودکار در این برنامه؛ در صورت نیاز با دانلود/Import دستی منتقل کنید. |
| FLUX محلی **اختیاری** | فقط اگر مالک خودش توکن Cloudflare و Account ID را در تنظیمات Windows وارد کند، Explorer به مدل `FLUX.1-schnell` دسترسی محدود دارد. این مسیر «پیش‌فرضِ دارای کلید» نیست و هزینه/اجرا تأیید جداگانه می‌خواهد. |
| **Kling** | **فقط MCP رسمی** `https://kling.ai/mcp` با SDK MCP و OAuth/PKCE در مرورگر خودِ مالک؛ بدون CLI، AK/SK یا کپی توکن. ابزار `who_am_i` نخست برای راستی‌آزمایی هویت/مدل‌ها، سپس `tools/list` و `tools/call` با آرگومان JSON بر اساس schema واقعی سرور. |

اتصال مستقیم YouTube/Google OAuth، Telegram Bot/Gateway و Manus از استودیو حذف شده است؛ وجود کلیدهای YouTube در پورتال مجوز خواندن یا انتقال آن‌ها به EXE نیست. بر اساس [فهرست رسمی ۱۶ پلتفرم](https://docs.zernio.com/platforms)، [راهنمای YouTube](https://docs.zernio.com/platforms/youtube)، [Telegram](https://docs.zernio.com/platforms/telegram) و [Instagram](https://docs.zernio.com/platforms/instagram)، انتشار به **۱۵ مقصد پستِ این فرم** از `POST /v1/posts` با `platform` و `accountId` انجام می‌شود؛ گزینه‌های اختصاصی مثل عنوان/visibility ویدئو یا `parseMode` در `platformSpecificData` هستند. [WhatsApp در Zernio](https://docs.zernio.com/platforms/whatsapp) مقصد این endpoint نیست: پیام از `POST /v1/inbox/conversations` و برادکست از `POST /v1/broadcasts`، با قواعد قالب/رضایت مخاطب/هزینهٔ خودشان انجام می‌شود؛ **اتصال مستقیم WhatsApp به استودیو اضافه نشده است**. [راهنمای رسمی ساخت پست](https://docs.zernio.com/posts/create-post) `Idempotency-Key` را برای retry همان پست در بازهٔ ۲۴ ساعت توصیه می‌کند؛ `x-request-id` جایگزین آن برای بدنهٔ تغییرکرده نیست. پوشش هر قابلیت تابع اتصال حساب، سطح دسترسی، محدودیت پلتفرم و طرح سرویس Zernio است؛ به معنی دسترسی بالفعل به همهٔ حساب‌ها نیست.

## چرخهٔ پژوهش → پیش‌نویس → Zernio (دو سند جدید)

1. در نمای «رصد و پژوهش»، RSS عمومی ثابت را بگیرید؛ **فقط سرنخ** است. مطلب اصلی و منبع مستقل را واقعاً بخوانید، تاریخ/نسخهٔ بازی و نیاز مخاطب را بررسی کنید و گزارش محلی دارای اولویت دستی و نسخه‌های ترکی مخصوص هر کانال را ذخیره کنید. گزارش با DPAPI محلی رمز می‌شود؛ `verifiedBySoftware:false` هیچ‌گاه فقط به سبب داشتن URL تغییر نمی‌کند. ساخت خودکار کاروسل چهاراسلایدی یا انتشار بلاگ پورتال انجام نمی‌شود.
2. در نمای Zernio «کشف حساب‌ها و سلامت دسترسی» را بزنید؛ `accountId` و `profileId` فقط از [پاسخ زندهٔ خود Zernio](https://docs.zernio.com/accounts/list-accounts) انتخاب شوند. اول Draft بسازید، سپس متن/رسانه/زمان آینده و مقصد را برای پنجرهٔ تأیید مالک آماده کنید. **زمان گذشته در Zernio می‌تواند فوراً نشر شود**؛ برنامه جلوی آن را می‌گیرد. پس از اجرا `GET /v1/posts/{id}` و نتیجهٔ هر مقصد را چک کنید؛ ۲۰۲/۲۰۷/۴۰۹/خطای شبکه، موفقیت قطعی نیستند.
3. برای CTA دارای کلیدواژه، فرم هدایت‌شده انتشار مستقیم را متوقف می‌کند: محتوای وعده‌داده‌شده را آماده کنید، Draft را بسازید، اتوماسیون را به `postId` همان Draft با keyword و DM واقعی وصل کنید، خواندن inbox را تست و تحویل مجاز را جدا اثبات کنید. سپس [در Explorer با PUT](https://docs.zernio.com/posts/update-post) و `isDraft:false` و زمان آینده، **همان Draft** را ارتقا دهید؛ پیش از آن هویت پست و حساب‌ها دوباره خوانده می‌شوند. PUT کلید idempotency مستند ندارد؛ در پاسخ نامطمئن اول status را بخوانید. اتوماسیون DM ممکن است با ساخت فعال شود؛ relay حتی با تأیید خودکار عمومی برای نوشتن‌های پیام‌رسانی تأیید مستقل مالک می‌خواهد.
4. در بازبینی روزانه، آمار، وضعیت انتشار و لاگ ارسال Zernio را با گزارش محلی تطبیق دهید. الگوریتم مستقل بهترین زمان، صحت‌سنجی AI، خواندن همهٔ منابع مورد اشارهٔ دستورالعمل‌ها، تولید خودکار محتوا و ارسال خودکار روزانه **پیاده/فعال نشده‌اند**. دسترسی Analytics به پلن و حساب وابسته است.

برای ایجنت جفت‌شده روی شاخهٔ ثابت، فرمان‌های **خواندنی** `node agent-client.cjs access`، `research [feed-ids]`، `editorial list` و `engagement-check <accountId>` وجود دارند؛ `editorial save <json-file-outside-repo> --confirm-write` یک یادداشت محلی است. `api zernio POST /v1/posts '{...}' --confirm-write [--idempotency=UUID]` با کلید تصادفی پیش‌فرض فقط **در صورت مجوز مشخص مالک** باید اجرا شود. `--confirm-write`، اتصال حساب یا جفت‌سازی به‌تنهایی مجوز پست/DM/هزینه نیستند. مشخصات دسترسی، کارهای باز و ترتیب کار در [ماتریس](../Doc/access-and-execution-matrix-fa.md) آمده است.

### Vault پورتال و تنظیمات محلی

مسیر `PUT /api/admin/integration-secrets/:key` برای **نوشتن** است؛ طبق بررسی [کد Vault در شاخهٔ مرجع پورتال، commit `843cfb3`](https://github.com/paymanshafayan/bazino-gamenet-portal/blob/843cfb3b29d89b32407c67099e7dae2e2339ba68/server/publishing/settings.ts)، کلید AES-256-GCM فقط با `BAZINO_SECRETS_KEY` سمت Railway رمزگشایی می‌شود و مرکز کلیدها مقدار را ماسک‌شده نشان می‌دهد. نه دادهٔ رمزگذاری‌شدهٔ داخل Git کلید واقعی است، نه API خواندن مقدار خام برای برنامهٔ Windows وجود دارد. توکن YouTube و FLUX را از Vault بیرون نمی‌کشیم و در EXE، workflow یا ریپو قرار نمی‌دهیم. استفادهٔ بدون ورود مجدد کلید FLUX از طریق **ورود مالک به پنل پورتال** و تولید تصویر در همان پنل انجام می‌شود؛ استودیو به‌طور خودکار به نشست ادمین یا Vault متصل نمی‌شود. برای اجرای **مستقیم Zernio در برنامه** هنوز کلید API Zernio لازم است؛ تا ایجاد یک سرویس/جفت‌سازی محدود و معتبر سمت پورتال، ادعای راه‌اندازی بدون کلید Zernio نداریم.

مرورگر محلی فقط به سرور loopback همان Windows درخواست **نسبی** می‌فرستد؛ Host/Origin و توکن تصادفی session بررسی می‌شوند. کلیدهای محلیِ مجاز (GitHub، Zernio و در صورت انتخاب مالک Cloudflare) و دادهٔ OAuth Kling با **Windows DPAPI در حساب همان کاربر** زیر `%APPDATA%\BazinoMarketingBrowser\vault.json` رمز می‌شوند. دستگاه دیگر نمی‌تواند آن فایل را باز کند. نسخهٔ جدید اگر Vault محلی قدیمی وجود داشته باشد، کلیدهای مستقیمِ منسوخ‌شدهٔ YouTube/Telegram/Manus را از آن حذف می‌کند، ولی Vault سرور پورتال دست‌نخورده می‌ماند. کلیدهای نسخهٔ Electron به‌طور خودکار مهاجرت نمی‌کنند. هیچ کلید/کوکی/کد ورود در چت یا ریپو قرار نگیرد.

ارسال عملیات ایجنت از مسیر رمزگذاری‌شده/امضاشدهٔ `desktop-app/relay` روی **فقط همین شاخهٔ کاری** انجام می‌شود؛ هر درخواست نوشتنی پیش‌فرض در Windows با پنجرهٔ بومی تأیید جداگانه می‌خواهد. کلید GitHub مالک باید fine-grained، فقط برای ریپوی **private** با `Contents: Read and write` باشد؛ کلید فقط در Windows وارد می‌شود. برای جفت‌سازی، ابتدا برنامه را در Windows باز و **GitHub Connect** کنید؛ سپس ایجنت روی شاخهٔ clean `node "استودیوی تبلیغات و بازاریابی/desktop-app/agent-client.cjs" pair` را اجرا و مالک اثر انگشت را با خروجی مستقیم و پنجرهٔ محلی مقایسه می‌کند. دستور `status` اثر انگشت دستگاه را نشان می‌دهد؛ ایجنت پس از تأیید مستقل مالک، `BAZINO_DESKTOP_FINGERPRINT` را محلی تنظیم می‌کند. **هیچ دستور خودکارِ انتشار/هزینه‌کرد صرفاً با اتصال مجاز نمی‌شود.**

## Kling MCP / مجوز حساب

1. در Windows مالک دکمهٔ **اتصال Kling MCP** را بزنید و در مرورگرِ همان رایانه OAuth Kling را خودتان تأیید کنید. callback فقط روی `127.0.0.1:59677/kling-callback` گوش می‌دهد و PKCE/state بررسی می‌شود؛ نشانی/کد authorization در Git نوشته نمی‌شود.
2. برنامه تنها پس از نتیجهٔ موفق `who_am_i` پیام «OAuth verified» نشان می‌دهد. بعد از آن با دکمهٔ **ابزارهای حساب** schema واقعی پارامترهای ابزار را ببینید و برای فراخوانی JSON همان schema را وارد کنید. تنظیم URL سرور *Global* دقیقاً مطابق درخواست مالک است؛ کشور/نوع حساب را از روی حدس تعیین نمی‌کنیم. اگر حساب با این endpoint سازگار نبود، بدون تلاش برای دورزدن OAuth توقف کنید.
3. این کلاینت MCP **داخل برنامهٔ Windows** است، نه نصب MCP برای محیط خودِ Arena. در صورتی که بخواهید MCP را در Cursor/Claude نیز به‌طور مستقیم ثبت کنید، مطابق [راهنمای رسمی Kling](https://kling.ai/app/mcp/guide) connector `klingai` با URL `https://kling.ai/mcp` و Connect/Sign in را در خود آن کلاینت اضافه کنید؛ **ساخت config بدون OAuth یا `who_am_i` اتصال واقعی نیست**. برای یک ایجنت MCP و CLI را هم‌زمان نصب نکنید.

`file_upload` در MCP فقط ticket بارگذاری می‌دهد؛ انتقال خودکار بایت/فایل از داخل ابزار MCP در این نسخه پیاده نشده است. ابزارهای دیگر با JSON براساس schema برگشتی سرور فراخوانی می‌شوند و تنها پس از تأیید فردی اجازهٔ تولید/حذف دارند. طبق [سیاست رسمی Kling](https://kling.ai/app/mcp/guide)، برخی اعتبارهای bonus در MCP قابل استفاده نیست، تسک تولید پس از ارسال لغو نمی‌شود و URL فایل خروجی معمولاً ۲۴ ساعت اعتبار دارد. **هیچ تسک تولیدی در راه‌اندازی اجرا نشود** تا کاربر محتوا، مدل، هزینه و خروجی را صریحاً مشخص کند.

## شاهد تست و کارِ باقی‌مانده

`npm test` (۵۵/۵۵، شامل خروج آخرین تب، راه‌اندازی مجدد کنترل‌شدهٔ سرور، تشخیص پورت ناشناس، قطع login ناتمام Kling و بررسی ساختاری اسکریپت محلی) پوشش mock پروتکل GitHub، Zernio/FLUX، حذف مسیرهای مستقیم شبکه‌ها، پالایش Vault محلی، UI DOM، Host/Origin/session سرور محلی، جریان Kling MCP و گیت جدید (SSRF/DNS/redirect، registry، تأیید مستقل، OAuth/PKCE و اعتبارسنجی عملیات) را دارد. `npm run check` نحو JS را بررسی می‌کند. اجرای واقعی **نسخهٔ اصلاح‌شده** روی Windows/DPAPI، ورود به پورتال، FLUX، حساب‌های Zernio و **OAuth واقعی Kling** هنوز با حساب مالک راستی‌آزمایی نشده‌اند. اجرای اولیه و تلاش‌های مجدد Actions در آپلود با سهمیهٔ artifact شکست خوردند؛ آخرین خطا در ۲۰۲۶-۰۹-۲۶ ساعت ۰۵:۱۷ UTC بود. اکنون شمار artifact/cache ریپو صفر است، اما رفع سهمیه و وجود EXE قابل دانلود از GitHub هنوز اثبات نشده است.

Explorer مسیرهای JSON Zernio را فقط به مبدأ رسمی Zernio می‌فرستد و استفادهٔ محلی Cloudflare را به مسیر مدل FLUX محدود می‌کند. UI قالب پایهٔ انتشار **۱۵ مقصد پست Zernio** را دارد و `platformSpecificData` اختیاری را می‌پذیرد؛ WhatsApp از مسیر جداگانهٔ پیام/برادکست Zernio است و در فرم پست نمایش داده نمی‌شود. Explorer امکان نوشتن درخواست JSON به API رسمی Zernio را دارد، ولی UI اختصاصی یا آزمون ارسال واقعی واتس‌اپ نداریم؛ پیش از استفاده، اسناد مقصد، اتصال واقعی، رضایت مخاطب، قالب و هزینه را بررسی کنید. **هیچ انتشار/هزینه‌کرد یا کپی کلید از پورتال انجام نشده است.**
